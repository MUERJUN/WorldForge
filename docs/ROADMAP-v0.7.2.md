# v0.7.2 可行性分析与最小开发范围

基线：**v0.7.1**（`df335b4` / tag `v0.7.1`）。本轮**不做大型重构**，两个目标：**真实模型端到端验收** + **AI 直接理解和操作 Minecraft 世界**。

---

## 目标一：真实模型端到端验收

### 现状

- 仓库里**没有**任何打真实 API 的测试。v0.7.0 / v0.7.1 的 AI 验收全部用本地脚本化的 `MockToolProvider`——它证明的是**智能体链路**（准备→确认→再校验→执行→事件），**不是真实服务商的兼容性**。两个版本的已知限制里都写着这一条。
- `OpenAICompatibleProvider` 已经能发标准 Chat Completions 请求，但**没有发过 `tools[]`**，也没有解析过 `tool_calls`。

### 可行性

**可行，且不需要改产品代码。** 需要的是一个**独立的验收测试**：

| 要素 | 现状 | 需要做什么 |
|------|------|-----------|
| 端点 | `baseUrl + /chat/completions` | 已支持（OpenAI 兼容：DeepSeek / OpenAI / 任意兼容网关） |
| 鉴权 | `Authorization: Bearer <key>` | 已支持，key 只在服务端内存里 |
| `tools[]` | **未实现** | 在 provider 上加一个**可选**的 tools 分支（默认关闭，旧行为不变） |
| `tool_calls` 解析 | **未实现** | 同上，与 `ToolCallingSupport.parseResponse` 复用同一套解析 |
| 多轮工具循环 | **服务端已有**（`AgentOrchestrator`） | 验收测试直接驱动它，不需要新循环 |

**安全规则（硬性）**：

- 密钥**只**从环境变量 `WORLDFORGE_TEST_API_KEY` 读，**或**从一个 gitignore 的本地文件读；**永不**进仓库、**永不**进日志、**永不**进聊天历史。
- 没有密钥 → 测试用 JUnit 的 `assumeTrue` **跳过**并明确打印「未验证：没有可用的 API 密钥」。**不冒充通过。**
- 仓库里**不写**任何开发者机器的磁盘路径；本地密钥文件已在 `.gitignore`（`apikey.txt`、`**/apikey.txt`）。

### 验收覆盖（任务书要求的多轮工具调用）

一次真实会话里依次覆盖：

1. **聊天**：模型真的理解一句话并回答。
2. **工具参数**：模型真的发出 `tool_calls`，参数通过**严格 Schema 校验**（非法参数必须被拒绝，而不是"差不多就行"）。
3. **玩家确认**：模型请求写入 → 服务端**不执行** → 玩家确认 → 才执行。
4. **服务端实际修改**：确认后**真的**改到了服务端状态（不是模型自称）。
5. **失败处理**：非法参数、未知工具、权限不足 → 都被拒绝并带**稳定的错误码**。
6. **取消**：确认前取消 → **世界零变化**。

**每一步的断言都落在服务端真实状态上**，不在模型文本上。

### 最小开发范围

- provider 增加一个**可选**的原生 `tools[]` + `tool_calls` 分支（默认关闭 → v0.7.1 行为完全不变）。
- 新增 `RealModelAcceptanceTest`（JUnit，`@EnabledIfEnvironmentVariable` 或 `assumeTrue`）：无密钥即跳过并报告"未验证"。
- 一个本地脚本：把 `apikey.txt` 读进环境变量再跑测试（**不入库**）。

## 目标二：AI 直接理解和操作 Minecraft 世界

### 现状的硬限制

今天 AI 能改的**只有 WorldForge 自己的虚拟定义**（`worldforge:dynamic_item` / `worldforge:dynamic_block`）。原版物品**完全没有被 WorldForge 的行为引擎接管过**——仓库里**没有任何** `UseItemCallback` / `AttackEntityCallback` 之类的原版钩子；`BehaviorEngine.onRightClick` 只在 `DynamicItem`（虚拟物品）自己的 `use()` 里被调用。

所以「给我的**原版**钻石剑加上雷电」今天做不到，AI 只能建议你换一把虚拟剑——**这正是要突破的那一点**。

### 候选方案（比较）

| 方案 | 玩家手里的剑 | 可撤销 | 评价 |
|------|-------------|--------|------|
| **A. 嫁接行为组件**（推荐） | **还是原版钻石剑**（id、贴图、属性全不变），只多一个 WorldForge 行为组件 | ✅ 去掉组件即完全还原 | 真正的突破 |
| B. 替换成虚拟物品（现状） | 变成 `worldforge:dynamic_item`，**原剑消失** | 勉强 | 非破坏性差，且没突破 |
| C. 全局监听器 | 不针对具体物品 | 否 | 错：会对所有玩家的所有钻石剑生效 |

**⇒ 选 A。**

### 方案 A 的技术路径（与现有代码同构）

1. **新组件** `worldforge:behavior_graft`：挂在**任意** ItemStack 上的行为列表。
   - 组件注册方式与现有 `VIRTUAL_ID` / `BEHAVIOR_STATE` **完全一致**（codec + packetCodec）→ 客户端能正确同步 ✓
2. **行为引擎解析来源**：虚拟物品优先用定义；**没有虚拟定义时看嫁接组件**。冷却已经存在 `BEHAVIOR_STATE` 组件上（按栈），**天然对原版物品可用** ✓
3. **原版钩子**：`UseItemCallback`（右键）与 `AttackEntityCallback` / `HurtEntityCallback`（命中）。
   - 钩子里**跳过虚拟物品**（它自己已经处理过）→ 不会双触发
   - `fabric-item-api-v1` 已在依赖里 ✓
4. **两个新工具**（不是几十个）：
   - `graft_behavior`：给**玩家当前手持的物品**附加一个行为（按槽位改真实的栈）
   - `ungraft_behavior`：移除嫁接（**完全还原**）
5. **读侧扩展**：`inspect_context` 报告手持物品的**原版 id**、是否已嫁接、嫁接了什么；视线目标的原版 id。
6. **能力描述必须准确**（不能再撒谎）：
   - 物品：「**可以**给手中的原版物品附加行为，物品本身不变，随时可撤销」
   - 方块：「**原版方块不能直接改造**」→ 动态方块可改定义；原版方块只能**替换**成动态方块（会改变这个方块）

### 方块侧（同一循环内的第二条支线）

- 视线目标是 **WorldForge 动态方块** → 现有的 `modify_target_block`（改共享定义，会提示影响所有同 ID 实例）✓ 已有
- 视线目标是 **原版方块** → 说清限制，并提供「**替换成一个带该行为的动态方块**」；替换会改变世界，**记录原方块以便撤销**

### 最小开发范围（一个可玩、可验证、可撤销的闭环）

**只做一个闭环**：手持原版剑 → AI 读 → 摘要 → 确认 → **真的能放雷电** → 可撤销。

方块侧放在同一闭环里（读 + 动态方块改定义 + 原版方块的替换建议），但**不**在这一轮做大规模建筑编辑器。

### 明确的诚实边界（不假装）

- 嫁接**不是**修改原版物品的"定义"：原版物品没有定义可改；我们给它**加一个行为**。物品 id、贴图、附魔、耐久**都不变**。
- 嫁接行为写在**这个栈**上：换一把新剑不会继承；**部分合成/锻造可能丢失**嫁接（会在已知限制里写明）。
- 原版方块**不能**被"改造"；只能替换或保留。
- 行为白名单仍然有效（`right_click` / `hit_entity` + 7 个动作）——AI 不能创造新动作。

### 交互界面

- **不加**任何专业控制按钮、不加 IDE / 终端 / 调试面板 ✓
- 聊天里多出来的只是：一句"读到了什么"、一句"要做什么"、确认控件、和真实结果
- 撤销也走同一条聊天路径（`ungraft_behavior` 工具 + 聊天里的"撤销"）

## 门禁（一条都不能少）

- 全量 JUnit
- WorldForge GameTest（A/B/C 三条真实流程 + v0.7.1 的 6 个并发/确认/删除/取消用例）
- 独立 Mod GameTest（三工程真实构建）
- 真实客户端聊天自动化
- Linux CI（对最终发布提交）
- **新增**：嫁接闭环的 GameTest（嫁接 → 真的触发 → 撤销 → 栈完全还原）
- **新增**：真实模型验收测试（无密钥时**明确跳过并报告未验证**）

## 顺带维护（非本轮重点）

- GitHub Actions 的 Node.js 运行时弃用警告：把 `actions/checkout` / `actions/setup-java` 升到当前版本。

## 建议的提交顺序

1. `feat: 原版物品行为嫁接`（组件 + 行为引擎 + 钩子 + 工具 + 撤销）→ 门禁全绿
2. `feat: AI 读原版手持物品与视线方块`（读侧 + 能力描述修正）→ 门禁全绿
3. `feat: 真实模型端到端验收`（provider 的 tools 分支 + 验收测试 + 本地脚本）→ 门禁全绿
4. `chore: GitHub Actions 运行时维护`
5. 文档 + 发布
